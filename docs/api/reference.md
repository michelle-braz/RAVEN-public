# API reference

> Classification: Technical. Machine-readable contract: [openapi.json](openapi.json) (generated by
> `tools/export_openapi.py`; CI fails if it is stale). In development the same contract is served at `/docs`.

All examples use synthetic data.

## Authentication

Send the key in the `X-API-Key` header on every protected request. Public paths: `/`, `/health`, `/ready`,
`/status`, `/missions/*`, `/static/*` (and `/docs`, `/openapi.json` outside production).

| Key | Access |
|---|---|
| Operator (`RAVEN_API_KEY`) | Everything, including `/ops/metrics` and `/beta/business-proof` |
| Customer (`PRO_API_KEYS`, `BETA_KEYS_JSON` active entries) | Analysis and feedback endpoints, no daily quota |
| Customer, free tier (`FREE_API_KEYS`) | Same endpoints, 100 requests per day |

Ten failed key attempts from one client address within a minute lock that address out for the rest of the
window (429, `Retry-After: 60`), even for valid keys. Behind a proxy set `RAVEN_TRUSTED_PROXY_HOPS` so the real
client address is used.

## Endpoints

| Method and path | Auth | Purpose |
|---|---|---|
| `POST /v1/analyze` | key | Analyse one signal: the main endpoint |
| `POST /evaluate` | key | Legacy rule engine: integer score 0 to 100 (LOW, MEDIUM, HIGH) |
| `POST /beta/validate-resolution` | key | Record an analyst decision and, if approved, the validated resolution |
| `POST /beta/decision-impact` | key | Record a decision only |
| `GET /beta/impact-summary` | key | Aggregate decision metrics for this instance |
| `GET /beta/business-proof` | operator | Adoption metrics for the vendor |
| `GET /ops/metrics` | operator | Operational counters |
| `GET /health` | none | Liveness |
| `GET /ready` | none | Readiness: 200, or 503 when the pipeline is down or the data directory is not writable |
| `GET /status` | none | Version and uptime |
| `GET /missions/` | none | Cyber Missions |

The `/beta` prefix is historical and kept so existing integrations do not break; these endpoints are supported
feedback endpoints, not a preview.

## `POST /v1/analyze`

```http
POST /v1/analyze
Content-Type: application/json
X-API-Key: <key>

{"message": "Checkout API returned HTTP 503 after a configuration change in the synthetic staging environment",
 "source": "application"}
```

`message`: required, 1 to 8,192 characters, trimmed. `source`: `application`, `infrastructure`, `network`, `iam`,
`audit` or `unknown` (default). Requests are limited to 30 per minute per client address by default.

Response fields and what each one means:

| Field | Meaning |
|---|---|
| `request_id`, `incident_id` | Ids to quote when giving feedback. The incident id is stable for the same normalized signal at the same severity while it stays in the recurrence window |
| `risk_score`, `severity`, `priority` | Deterministic score 0.0 to 1.0; band LOW, MEDIUM, HIGH, CRITICAL |
| `confidence` | The risk score rescaled to 0 to 100. **Not** a calibrated probability of being right |
| `recommended_action` | ignore, group_as_noise, monitor, investigate or escalate, from the score (with deterministic escalation rules for authentication failures) |
| `evidence` | **Observed**: the scoring factors that fired. Never inference |
| `hypothesis` | **Heuristic**, to be verified by a human. Kept separate from evidence |
| `event_type`, `monitored_object` | Keyword-based classification and component guess; `unknown` when nothing matched |
| `context.related_alerts` | Repeats of this signal seen in the active window |
| `context.recent_deployment` | True when the message wording mentions a deployment or configuration change |
| `context.affected_services` | Only the detected object; RAVEN does not know your topology |
| `historical_context.occurrences_in_active_window` | Observed repeats in this process's memory (default one hour), not a 30-day history |
| `historical_context.suggested_playbook` | Generic starting point per event type, not a resolution learned from your incidents |
| `impact` | Severity-derived label with a `basis` note; not a measured impact |
| `recommended_steps` | Ordered generic investigation steps for the event type |
| `explain.factors` | Each scoring factor with weight and detail |
| `tier` | `pro` or `free` |

Example (abridged, real output):

```json
{
  "incident_id": "LOW-B0F578", "event_type": "deployment_related_failure", "monitored_object": "payment-service",
  "risk_score": 0.2657, "severity": "LOW", "recommended_action": "group_as_noise",
  "evidence": ["Risk score 0.27 — severity classified as LOW"],
  "context": {"related_alerts": 0, "recent_deployment": true, "affected_services": ["payment-service"]},
  "historical_context": {"occurrences_in_active_window": 1, "last_occurrence": "first occurrence in the active window",
                         "suggested_playbook": "Roll back to previous version; validate configuration and secrets"},
  "impact": {"affected_services": 1, "business_criticality": "low",
             "basis": "derived from severity and message wording; not a measured impact"},
  "hypothesis": "Failure directly correlated with recent deployment — rollback candidate"
}
```

## `POST /beta/validate-resolution`

Always records a decision impact. Creates a validated-incident record only when `memory_write_approved` is
`true` **and** `resolution_text` is present. Required: `incident_id`, `request_id`, `decision_taken`
(ACCEPT, REVIEW, BLOCK, IGNORE, INVESTIGATE, OTHER), `action_taken`, `confidence` (1 to 5),
`replaced_manual_process`, `time_saved_minutes`. Optional: `resolution_text` (up to 4,096), `hypothesis_correct`,
`validated_by` (up to 256), `signature`, `event_type`, `source`, `message_normalized`, `tokens` (up to 256),
`supersedes`. Returns 201 with `decision_impact_id`, `memory_record_created`, `memory_record_id`.

Validation limits: strings and lists are bounded; total request body at most 256 KiB by default.

## Errors

Every error uses one envelope, and no error reveals internals:

```json
{"error": "human readable message", "code": "machine_readable_code"}
```

| Status | `code` | When |
|---|---|---|
| 400 | `bad_request` | Body is not valid JSON |
| 401 | `missing_api_key` / `unauthorized` | No key, or key not accepted by the dependency |
| 403 | `invalid_api_key` / `forbidden` | Unknown or revoked key; operator key required |
| 404 | `not_found` | Unknown path |
| 411 / 413 | `length_required` / `payload_too_large` | Body without `Content-Length`, or over the cap |
| 422 | `validation_error` | Schema or value rule failed, or invalid Unicode |
| 429 | `rate_limit_exceeded` | Per-client limit, daily quota, failed-attempt lockout, or pipeline buffer full |
| 500 | `internal_server_error` | Unexpected; body carries `request_id` to give to support |
| 503 | `service_unavailable` | Decision could not be stored |

Every response carries `X-Request-ID` (a well-formed one you send is echoed; otherwise one is generated) and
`Cache-Control: no-store`.

## Compatibility policy

`/v1` is additive: new response fields and new optional request fields may appear; existing fields keep their
meaning. A change that removes or re-purposes a field ships in a new minor version and is listed in
[CHANGELOG](../../CHANGELOG.md). Clients must ignore unknown fields.
